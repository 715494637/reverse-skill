# JSVMP and AST Recovery

## 使用边界

仅在需要决定并记录当前目标的 JSVMP / AST 恢复应当做到多深时使用本参考。它是挂载在 `recover` 下的专题参考，不是第二份 recover 核心参考。

本文件只聚焦于：

- 选择 JSVMP 恢复深度
- 定义必需的恢复工件
- 判断 `recover` 何时应当切换到 `locate`、`runtime` 或 `validation`
- 保留后续的 AST / 控制流平坦化指引

不要把本文件扩展成完整的 recover 主干。唯一入口仍然是 `jsr-reverse`，主干仍然是 `intake -> evidence -> locate -> recover -> runtime -> validation -> handoff`。

## 恢复级别

### Level A：只提取关键 `opcode`

适用条件：

- 目标字段的写回边界已经明确
- 只需要少量 `opcode` 语义就能解释该字段

关注点：

- 只提取会触达目标字段的 `opcode`
- 只证明输入、输出与状态变化
- 一旦目标字段已经能解释清楚就停止

### Level B：恢复 dispatcher 与关键状态载体

适用条件：

- 不恢复 dispatcher 就无法理解 `opcode`
- 关键分支依赖寄存器、栈、上下文对象或常量池

关注点：

- 先恢复 dispatcher loop
- 再恢复关键状态载体
- 最后归并关键 `opcode` 家族

### Level C：最小反编译或最小解释器

适用条件：

- 必须重放多条路径
- 需要协议重建或批量执行
- `A` 和 `B` 级都无法支撑下游工作

关注点：

- 只做最小、可验证的反编译或解释执行
- 不做低价值的全量 beautify

硬性升级规则：

- 默认从 `A` 开始；不能因为代码脏、平坦化严重或字符串表复杂就直接跳到 `C`。
- 只有在满足以下至少一项时，才允许 `A -> B`：
  - 关键 `opcode` 若不恢复 dispatcher 语义就无法解释
  - 目标字段的解释依赖寄存器 / 栈 / 上下文流
  - 若不恢复状态载体，关键分支就无法判断
- 只有在满足以下至少一项时，才允许 `B -> C`：
  - 下游工作要求重放多条执行路径
  - 协议重建或批量执行要求最小可执行片段
  - `A` 和 `B` 级仍无法支撑 runtime 贴合或 validation 检查点

## JSVMP 专项工件

### 入口卡

必填字段：

- 目标字段或目标效果
- VM 入口函数 / 闭包
- bytecode 来源或 bytecode 加载器
- dispatcher 入口位置
- 解释执行函数 / 执行函数
- 与目标字段或目标写回路径的关系
- 最强观察锚点或证据
- 从可观测触发点到入口的调用链
- 用于证明的入口输入样本
- 入口的浏览器侧证据
- 入口的本地恢复解释
- 置信度与剩余未知项

### 状态载体卡

必填字段：

- 状态载体名称
- 载体类型：寄存器数组 / 栈对象 / 上下文对象 / 常量池 / 字符串表 / 其他
- 寄存器数组
- 栈对象
- 上下文对象
- 常量池 / 字符串表
- 初始化位置
- 与目标相关的读取点
- 与目标相关的写入点
- 迁移规则或更新规则
- 哪些载体实质影响目标字段
- 哪些载体只搬运状态而不影响判断
- 载体状态的浏览器侧证据
- 载体的本地恢复映射
- 为什么该载体对目标字段是关键的
- 剩余缺口

### 关键 `opcode` / 分支卡

必填字段：

- `opcode` 或分支标识符
- dispatcher 中的位置或可达条件
- 输入
- 输出
- 状态修改
- 依赖
- 证据
- 与目标字段 / hash / 加密 / 序列化 / 组包的关系
- 本地恢复语义
- 等价性结论：match / diverge / unproven
- 剩余阻塞项

### 恢复级别决策卡

必填字段：

- 当前选择的级别：`A` / `B` / `C`
- 当前级别为什么足够
- 为什么更浅的停止深度不够
- 为什么更深展开尚无必要，或为什么已经变得必要
- 若发生升级，触发升级的证明是什么
- 已经收口的检查点
- 仍然未收口的检查点
- 下一步必需的切换：`locate` / `runtime` / `validation` / stop
- 显式停止深度

## 阶段切换判据

### `recover -> locate`

当以下任一项仍然成立时，应回退到 `locate`：

- dispatcher 入口相关性仍未被证明
- 当前假定的 VM 入口仍然只是猜测，而不是已观察到的边界锚点
- 已恢复的 VM 切片仍无法绑到真实目标写回路径
- 继续深挖 VM 只会沿着未证实边界推进，而不能真正收口证据

当当前阻塞点仍然是边界识别，而不是 VM 语义本身时，应返回 `locate`，而不是继续扩展 VM 恢复。

### `recover -> runtime`

只有在以下任一项已经成立时，才允许切到 `runtime`：

- 桥接合同已经清楚
- 关键操作符 / `opcode` 家族已经足以解释算法边界
- 剩余分歧由环境事实、生命周期状态、时序或风险分支引起
- 继续深挖 VM 只会增加代码体量，却不能解释执行分歧

只有在 VM 行为到目标字段的已证实联系，已经足以支撑命名检查点时，才允许转到 `runtime`。

### `recover -> validation`

只有在以下各项都已成立时，才允许切到 `validation`：

- dispatcher 入口已知
- 状态载体已知
- 与目标字段相关的关键 `opcode` / 分支已提取
- 已选择的停止级别有充分理由
- 已存在可用于检查点对比的固定样本

如果卡片或检查点还不完整，不要切到 `validation`；要么继续留在 `recover` 补齐缺失检查点，要么根据真实阻塞回退到 `locate` 或前进到 `runtime`。

## 检查点合同

必需检查点：

- dispatcher 入口状态
- 关键状态载体迁移
- 关键 `opcode` 输入 / 输出
- 写回前中间结果
- 最终目标字段

对每个检查点都要记录：

- 固定输入样本
- 浏览器侧证据
- 恢复后 / 本地侧证据
- 结论：match / diverge / unproven
- 剩余缺口

必须按检查点收口，而不是只看最终结果。

## 常见误判

- 不要把 dispatcher 恢复本身当作完成。
- 不要把字符串表恢复当作算法恢复完成。
- 不要因为代码风格脏乱就直接跳到 `C`
- 当剩余阻塞已经明显是 runtime 分歧时，不要继续深挖 VM。
- 在状态与运行时依赖尚未排除前，不要宣称“纯算法”

## 完成标准

只有当以下各项都被明确写出时，恢复才算完成：

- 停在 `A`、`B` 或 `C` 的停止深度有证据支撑。
- 必需的卡片与检查点已经作为工件记录下来，而不是只在正文里隐含提到。
- 恢复结果已经解释了目标字段，或者明确写出剩余缺口。
- 下一步切换已经明确：回到 `locate`、前进到 `runtime`、前进到 `validation`，或者停止。
- 切换理由反映的是真实阻塞，而不是偏好继续扩展更深的 VM。

## JSVMP 的基本顺序

### Step 1：找到入口

先找清：

- bytecode 从哪里来
- dispatcher loop 从哪里开始
- 哪个函数负责解释执行

### Step 2：识别状态载体

优先识别：

- 寄存器数组
- 栈对象
- 上下文对象
- 常量池与字符串表

### Step 3：提取关键 `opcode`

不要一开始就试图重建整个虚拟机。

先回答：

- 哪些 `opcode` 直接触达目标字段
- 哪些 `opcode` 负责 hash、加密、序列化或组包
- 哪些 `opcode` 只是搬运状态

### Step 4：做等价性检查

每提取完一段切片，就做输入 / 输出对比。不要只凭“看起来像”下判断。

## AST 与控制流平坦化的基本顺序

不要仅仅为了可读性就重写或规范化整个 AST。只恢复当前目标与检查点所需的锚点、执行顺序和带副作用的分支。

### Step 1：先恢复可读锚点

先恢复：

- 字面量
- 字符串表
- 对象 key
- 调用关系

### Step 2：识别平坦化 dispatcher

重点关注：

- 顶层 `switch`
- 跳转状态变量
- 死分支与诱饵分支

### Step 3：恢复真实执行顺序

判断依据是执行顺序，不是 beautify 后的源码顺序。

### Step 4：分离副作用

要分清：

- 只是控制流包装的部分
- 真正会修改状态、请求数据或返回值的分支
