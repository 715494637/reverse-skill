# JSVMP 与 AST

## 一、先判 VMP 恢复级别

### A 级：只抽关键 `opcode`

适合：

- 已知目标字段写回边界
- 只差少量 `opcode` 语义就能解释目标字段

重点：

- 只抽会触碰目标字段的 `opcode`
- 只证明输入、输出、状态变化
- 能解释目标字段就停手

### B 级：恢复 dispatcher + 关键状态载体

适合：

- 不恢复 dispatcher 就无法读懂 `opcode`
- 关键分支依赖寄存器、栈、上下文对象或常量池

重点：

- 先恢复 dispatcher 循环
- 再恢复关键状态载体
- 最后归并关键 `opcode` 族

### C 级：最小反编译 / 最小解释器

适合：

- 需要多路径回放
- 需要协议重建或批量执行
- `A / B` 级无法支撑后续工作

重点：

- 只做最小可验证反编译 / 解释执行
- 不进行低收益的全量外观整理

升级原则：

- 默认从 `A` 开始。
- 只有证据证明当前级别不够，才升级。
- 能在低一级别解决，就不要进入高一级别。

## 二、处理 JSVMP 的基本顺序

### 第一步：定入口

先找：

- 字节码从哪里来
- 调度循环从哪里开始
- 哪个函数负责解释执行

### 第二步：定状态载体

重点看：

- 寄存器数组
- 栈对象
- 上下文对象
- 常量池 / 字符串表

### 第三步：抽关键 `opcode`

初始阶段不进行整台虚拟机恢复。

应该先回答：

- 哪些 `opcode` 会触碰目标字段
- 哪些 `opcode` 会做散列、加密、序列化、拼包
- 哪些 `opcode` 只是搬运状态

### 第四步：做等价验证

每抽出一段逻辑，就做输入输出对照，不要凭视觉判断。

## 三、处理 AST / 控制流平坦化的基本顺序

### 第一步：恢复可读锚点

先恢复：

- 字面量
- 字符串表
- 对象键
- 调用关系

### 第二步：识别平坦化分发器

重点识别：

- 总 `switch`
- 跳转状态变量
- 死分支与诱饵分支

### 第三步：恢复真实分支顺序

分析依据应为执行顺序，而不是格式化后的书写顺序。

### 第四步：把副作用分离出来

区分：

- 只是控制流包装
- 真正会改状态、改请求、改返回值的分支

## 四、常见误判

- 把分发器当核心算法。
- 把字符串表还原当成恢复完成。
- 把平坦化后的某个 case 当真实主路径。
- 直接进入 `C` 级整机恢复。
- 未进行等价性验证，仅依据外观相似判断。

## 五、处理完成的标准

- 已知调度入口。
- 已知状态载体。
- 已抽出与目标字段直接相关的关键分支或 `opcode`。
- 已知当前停在 `A / B / C` 的哪一级，以及为什么不继续下钻。
- 已能用恢复结果解释目标字段或支撑下一步复现。
