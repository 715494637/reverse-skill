# WASM、Worker、Webpack

## 一、先确定桥接层，再进入内部实现

这三类问题的共同点是：

- 真逻辑不一定直接暴露在主线程或源码表面。
- 但输入输出边界一定存在。

所以第一步永远是：

- 找入口
- 找桥接
- 找入参
- 找回参

## 二、Worker

优先确认：

- 是独立文件、`blob` 还是字符串拼装
- 主线程传了什么
- `worker` 回了什么
- 是否夹带一次性挑战、设备种子、会话态

默认记录格式：

```markdown
worker 入口：
主线程入参：
worker 回参：
共享状态：
最终写回位置：
```

桥接契约卡片：

```markdown
桥接类型：worker
入口：new Worker / blob / 字符串拼装
主线程 -> worker：
worker -> 主线程：
共享状态：cookie / storage / challenge / device seed / session
写回位置：
是否适合黑盒复用：是 / 否
```

## 三、WASM

优先确认：

- `imports` 需要什么
- `exports` 暴露什么
- JS 包装层如何组织参数
- 结果是直接返回，还是经过二次壳包装

结论：

- 如果桥接层已足以解释输入输出，则无需进行全量反汇编。

桥接契约卡片：

```markdown
桥接类型：wasm
加载入口：instantiate / instantiateStreaming
imports：
exports：
参数打包方式：
返回值回收方式：
二次包装层：
是否适合黑盒复用：是 / 否
```

## 四、Webpack / runtime

优先确认：

- 模块装载入口
- 懒加载点
- 真正目标模块是哪一个
- runtime 壳和业务模块的边界

高频误判包括：

- 长时间停留在 runtime 壳层，未进入业务模块。

模块闭包记录：

```markdown
目标模块：
直接依赖模块：
runtime helper：
需要导出的入口：
环境桩：
最小可运行闭包：
版本锚点（bundle/hash/moduleId）：
```

## 五、何时说明桥接层才是主难点

- 主线程只看到壳，真实值在回调、消息、内存或懒加载模块里出现。
- 改一层外壳并不能解释最终值怎么形成。
- 只有把桥接契约写清楚，下游才能继续做定位或复现。

## 六、完成标准

- 已有桥接契约。
- 已知入参、回参、写回点。
- `webpack` 场景下已知模块闭包边界。
- 已区分容器层、桥接层和业务层。
