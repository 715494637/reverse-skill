# Runtime Diagnosis

## 目的 / 使用边界

`runtime` 负责在边界与壳层都已经足够清楚的前提下，对浏览器执行与本地/受控执行的不一致进行分类。

使用本参考，是为了找出第一个有意义的分叉点，并为下一步动作给出最小运行时交接信号。

这个文件不是 runtime 工作板模板，也不是全局路由矩阵。

## Runtime 负责什么

`runtime` 只负责：

- 分类当前运行时问题
- 对比浏览器正常态与本地执行，找出首个分叉点
- 区分缺对象与缺状态
- 在后续比对前先稳定不稳定来源
- 说明 patch、拟合或 validation 所需的最小交接信号

## 默认诊断模型

先分类，再 patch。

运行时问题至少分为五类：

- `missing object`
- `missing state`
- `anti-debugging`
- `unstable source`
- `risk branch`

大多数失败都不是单一缺对象，而是多类问题的组合。

从一个“首个分叉点对比表”开始：

```markdown
| 项目 | 浏览器正常态 | 本地执行 | 差异 |
|---|---|---|---|
| 输入参数 | 相同 | 相同 | 否 |
| cookie / storage | 完整 | 缺失 | 是 |
| Date.now | 固定样本 | 固定样本 | 否 |
| Math.random | 固定样本 | 固定样本 | 否 |
| 中间值1 | 正常 | 正常 | 否 |
| 中间值2 | 正常 | 异常 | 是 |
| 最终响应 | 正常数据 | 风控态 | 是 |
```

用这张表把问题收缩到第一层出现分叉的位置。不要一上来就列大 patch 清单。

## Divergence Classes

### Missing object

常见信号：

- 报错提示缺少 `window`、`document`、`navigator`、`crypto`，或其他被直接访问的对象

必须验证：

- 当前链路确实会触达这个对象
- 移除或恢复这个对象时，失败点会稳定复现

### Missing state

常见信号：

- 不崩溃，但请求一直失败、输出错误，或始终进入风控态

必须验证：

- 即使对象都存在，链路仍然无法进入正常态
- 一旦补回上游响应、`cookie`、storage 或 challenge 状态，结果就有明确改善

不要把对象表面不完整和生命周期产出的状态混为一谈。缺少 `HttpOnly` cookie 是状态缺口，不是对象缺口。

### Anti-debugging

常见信号：

- 断点导致执行冻结
- 无穷 `debugger`
- 控制台一打开输出就变化
- 完整性校验或栈探针改变了分支行为

必须验证：

- 当前分叉究竟是调试摩擦本身导致，还是调试只是让其他运行时依赖暴露出来

### Unstable source

常见信号：

- 相同输入下，不同运行之间的中间值或输出仍然变化

要先稳定：

- `Date.now()`
- `performance.now()`
- `Math.random()`
- device seed、指纹 seed、安装时间、会话序列

不先稳定，后续对比都不够有力。

### Risk branch

常见信号：

- 浏览器有时正常，但本地回放或调试时稳定进入另一条分支

必须验证：

- 正常态与风控态第一次分叉发生在哪里
- 当前消费点属于风控分支，而不是目标 builder 本体

## 必要诊断输出

诊断输出必须保持最小化、可交接，至少包括：

- 问题类别或组合类别
- 第一个已确认分叉点
- 当前阻塞属于 `missing object`、`missing state`、`anti-debugging`、`unstable source`、`risk branch` 中哪一种
- 哪些事实需要写入 `请求链路.md` 的 `运行时补充` 小节
- 下一步动作是什么：补对象、补状态、稳定来源、隔离反调试，还是验证分支差异

对于 `deviceId`、`blackbox`、`sensor_data`、challenge、slider、risk-cookie` 这类指纹密集型目标，要保持诊断简短但明确：

- 采集了哪些指纹表面
- 哪些表面真的被聚合器消费
- 哪些已消费表面会影响目标字段或风控分支

最小交接信号：

- `missing object` -> 指出精确对象，以及当前链路确实触达它的证明
- `missing state` -> 指出必须补回的具体状态载体或上游响应
- `anti-debugging` -> 指出阻塞探针或分支，以及最小中和目标
- `unstable source` -> 指出必须先固定的来源
- `risk branch` -> 指出第一次风控分叉，以及触发分叉的状态差异

## 停止 / 交接标准

当下面几点都已明确时，`runtime` 可以停止：

- 分叉类别已经清楚
- 已知浏览器与本地执行第一次在哪一层分叉
- 缺对象与缺状态已被分开
- 不稳定来源已被固定，或已被明确列为当前主阻塞
- 下一份工件更新或 validation 动作已经清楚

此时应通过更新 `请求链路.md` 的 `运行时补充` 小节来交接已确认的 runtime 事实；若还有剩余证明缺口，再在同一文件的 `验证补充` 小节标出。

## 不负责什么

`runtime` 不负责：

- 从头证明请求链
- 当真正阻塞仍是隐藏逻辑时继续做壳层恢复
- 定义 `请求链路.md` 中 `运行时补充` 小节的完整模板
- 重复解释 `SKILL.md` 中的全局阶段路由
- 仅凭最终输出相似就宣称等价
