# 瑞数运行时与 Basearr 闭合

## 适用场景

当当前任务命中下面这些瑞数运行时表现时，使用本参考：

- 浏览器和本地生成的瑞数 `cookie` 或 token 不一致
- 目标存在额外 debugger 或 `hasDebug` 版本
- 怀疑不同站点的 `basearr` 存在差异
- 输出会随着时间、随机数、执行窗口变化
- 第一跳状态已经产出，但第二跳消费仍然失败

不要因为任务提到 `cookie` 就默认走这里。

## 先分清主阻塞项

扩大 patch 范围前，先把当前阻塞项分类成且只分类成一个主类：

| 主类 | 必须证明什么 |
| --- | --- |
| `hasDebug` 分支 | 当前工件是否属于额外 debugger 路线 |
| `basearr` 闭合 | 站点适配、数组形态和首层长度是否闭合 |
| 固定运行时事实 | 是否需要先冻结一小组浏览器形态事实才能对比 |
| 第二跳消费 | 产出状态是否只会在下一跳被接受 |

主类都说不清时，当前路线仍然是 `部分完成`。

## Basearr 闭合项

对瑞数 `cookie` 生成来说，下面这些都是闭合项，不是附注：

- 站点 hostname 适配路线
- `encryptLens`
- `lastWord` 这类 cookie key 后缀
- 每站点不同的 `flag`
- 当前分支是否需要 `hasDebug`

这些项只要还有一项没闭合，就不能宣称 `cookie` 已稳定复现。

## 优先冻结的运行时事实

在大范围补浏览器面之前，先检查这组更像瑞数最小模板的事实：

| 运行时事实 | 作用 |
| --- | --- |
| `window.name` | 状态或标识传递 |
| `navigator.maxTouchPoints` | 指纹分支选择 |
| `navigator.battery` | 浏览器形态契约 |
| `navigator.connection` | 浏览器形态契约 |
| `currentTime / runTime / startTime` | 时间窗和时间编码关系 |
| `random` | 随机相关编码与分支稳定性 |
| 执行窗口或循环次数代理量 | 时间驱动字段 |

这是一组优先检查项，不代表可以忽略其他依赖。

## 验收规则

- 没固定时间和随机源，不能宣称瑞数 `cookie` 稳定
- 没记录 `basearr` 闭合状态，不能宣称瑞数 `cookie` 稳定
- 第一跳状态后续还会被消费时，没有完成第二跳验证，就不能接受当前路线
- 如果输出长度或首层加密数组长度在波动，先按 `basearr` 或固定源问题处理，不要先扩大 patch 范围
- 额外 debugger 版本是路线分叉，不是普通反调试噪音

## `部分完成` 条件

下面任一项没闭合时，runtime 都应停在 `部分完成`：

- `hasDebug` 分支未确定
- `basearr`、`encryptLens`、`lastWord` 或 `flag` 未确定
- 用于比较的固定运行时事实还没冻结
- 第一跳状态后续要消费，但第二跳验证还没做
