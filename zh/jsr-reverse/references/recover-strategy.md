# Recovery Strategy

## 目的 / 使用边界

`recover` 阶段负责围绕已证明的边界压缩壳层，直到下一个工作能够建立在一个可读、可调用或可验证的逻辑契约之上。

只有在 `locate` 已经把目标请求、写入边界、sink 或上游依赖链证明到足以支撑下钻时，才使用本参考。

`recover` 不是第二套全局工作流。它只是一个阶段方法，用来决定先开哪一层、开多深、何时停止。

## Recover 负责什么

`recover` 只负责让下游工作成为可能所需的恢复工作：

- 为当前边界识别恢复目标
- 判断第一层应该从哪里开
- 选择最小恢复级别 `A / B / C`
- 当无需反编译时保留 black-box reuse 边界
- 记录当前停止深度已经足够的证明

## 默认工作模型

从三个问题开始：

1. 当前真正挡路的是哪一层：外层容器、dispatcher、状态载体、bridge，还是核心算子？
2. 当前任务需要的是语义说明、关键算子切片，还是最小重建？
3. 在哪一层可以停止，同时仍能支撑下游 runtime 或 validation？

选择第一层打开位置的默认顺序：

| 现象 | 第一层打开位置 |
|---|---|
| 仍找不到真实可调用路径 | 外层容器 |
| 大量 switch table 或 VM 风格控制流 | dispatcher 层 |
| 调用看得见，但参数 / 状态仍不透明 | 状态载体 |
| 逻辑只在 `worker`、`wasm` 或 loader callback 后出现 | bridge 层 |
| 写回点已知，但算法仍不透明 | 核心算子 |

## Recovery Targets

在继续下钻前，先选定一个目标：

### 1. 语义说明

只恢复足以回答以下问题的结构：

- 每一层负责什么
- 目标值沿着哪条路径流动
- 哪些输入控制输出

当下游需要的是边界语义，而不是可执行重建时，使用它。

### 2. 关键算子提炼

只恢复当前仍在挡路的最小不透明单元，例如：

- 关键 `opcode`
- 关键序列化壳层
- 关键 bridge 函数

当 builder 已知，而真正遮蔽的是核心算子时，使用它。

### 3. 最小重建

把所需路径重新拼成最小可验证片段。

只有在输入 / 输出边界已知，且已有稳定验证样本时，才使用它。

## Recovery Levels

默认从 `A` 级开始。只有证据表明当前级别无法支撑下一阶段时，才升级。

### Level A：只提取关键 `opcode`

适用条件：

- 写回边界已经明确
- 少量 `opcode` 语义就足以解释目标字段

交付物：

- 关键 `opcode` 卡片
- 输入 / 输出对照
- 目标字段形成路径

### Level B：恢复 dispatcher 与关键状态载体

适用条件：

- `opcode` 含义依赖 dispatcher、寄存器、栈或上下文
- 没有状态流就无法判断关键分支

交付物：

- dispatcher loop
- 关键状态载体
- 带状态流的 `opcode` 家族

### Level C：最小反编译或最小解释器

适用条件：

- 必须重放多条路径
- 需要协议重建、批量执行或最小可执行重建
- `A` / `B` 级都不足以支撑下游工作

交付物：

- 最小反编译结果或最小解释器
- 关键路径验证样本

## Black-Box Reuse Boundary

对于 `webpack/runtime`、`worker` 与部分 `wasm` 包裹层，black-box reuse 往往比继续深挖反编译更优。

适合 black-box reuse 的信号：

- 输入 / 输出边界已知
- 目标模块或 bridge 入口已找到
- 真正困难主要在容器壳层或 bridge 调用，而不是业务算子本体

不适合 black-box reuse 的信号：

- 目标模块依赖大量隐式共享状态
- 不恢复状态载体就无法稳定回放
- 模块本身又是另一层 `jsvmp` 或深协议壳

决策记录用简短格式：

```markdown
- 复用方式：black-box reuse / deeper recovery
- 复用边界：
- 已知输入：
- 已知输出：
- 仍依赖的状态载体：
- 不继续下钻的理由：
```

## 停止 / 完成标准

满足以下任一情况时，`recover` 可以停止：

- 目标字段形成路径已经解释到足以支撑下游证明
- bridge 契约与关键算子已经足以支撑 runtime 拟合或 validation
- 当前恢复级别已足够支撑下一任务，无需更深打开
- 继续下钻只会增加代码体积，不会增强结论

要证明“可以停”，记录里至少要能看出：

- 当前层职责明确
- 输入、输出或 bridge 跳转有稳定锚点
- 为什么在 `A / B / C` 中停在当前深度是合理的
- black-box reuse 是被接受还是被排除，以及对应边界证据
- 剩余缺口已经被明确归类为下游 runtime 或 validation 问题，而不是被藏在 recover 里

## 不负责什么

`recover` 不负责：

- 从零开始证明真实请求链
- 重新执行全局阶段路由
- 分类浏览器 / 本地执行分叉
- 定义运行时工件格式
- 在没有检查点证明时宣称等价
- 在尚未排除 runtime 依赖前，把路径认定为纯计算迁移

在宣称“可纯计算迁移”前，以下依赖类别必须已被其他地方排除，或在当前证据中被明确闭环：

1. 上游响应字段
2. `HttpOnly cookie`
3. 一次性 challenge、nonce 或 ticket
4. 浏览器内部状态
5. 指纹采集结果
6. 时间窗口、序列或续期依赖
