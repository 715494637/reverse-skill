# 瑞数恢复锚点

## 适用场景

当存在瑞数壳层，且下游需要比“代码格式化后更好看”更强的语义锚点时，使用本参考：

- 已拿到 `r2mKa` 调度文本
- 已拿到 `$_ts` 样本，且 `cp` 字段与恢复有关
- keys 路径被 `cp3`、动态任务或偏移量遮住
- 页面渲染或 appcode 被包在 `$_ts.l__` 中

本参考只负责：

- 选择瑞数专用恢复锚点
- 只恢复支撑下游所需的结构
- 不做没有边界的大段 beautify

## 推荐锚点顺序

除非证据表明依赖关系更紧，否则按下面顺序：

| 锚点 | 能证明什么 |
| --- | --- |
| `r2mKa` 文本 | dispatcher 树、任务族、子节点关系、稳定解析入口 |
| `cp0 / cp2 / cp6` | 解码后的常量、表层字符串、控制线索 |
| `cp3 -> dynamicTaskOffset -> keys` | 解密路径和 key material 的生成关系 |
| `$_ts.l__` appcode | 真正参与下游的页面渲染或解密代码 |

只要这些锚点已经存在，就不要先从整份 beautify 过的大包源码硬抠。

## 各锚点的恢复规则

- 先把 `r2mKa` 当 dispatcher / task-tree 锚点恢复，不把它直接当最终业务算子。
- 先解 `cp0 / cp2 / cp6`，再扩大算子分析；它们经常先给出稳定命名、常量或控制线索。
- 把 keys 路径当桥接关系看：`cp3 -> task offset -> keys`，不要当成孤立的字符串解密技巧。
- 把 `$_ts.l__` 当承载渲染代码或解密代码的桥接工件，不当成页面噪音。

## 验证检查点

每拿下一层锚点，就补一条检查点：

- `r2mKa`：解析入口或任务关系稳定
- `cp` 层：解码输出已稳定到足以支持命名或控制判断
- keys 路径：key material 生成路径已稳定到足以做下游验证
- `$_ts.l__`：已得到稳定输出，或已得到稳定停止原因

如果当前锚点连检查点都说不清，就还不能交接给下游。

## 停止条件

- 没有稳定 `$_ts` 样本，也没有 `r2mKa` 或 appcode 锚点：`阻塞`
- 锚点已知，但 keys 路径或 appcode 语义还没闭合：`部分完成`
- 真正阻塞项是 `hasDebug`、固定时间随机源或第二跳接受条件：切 `$jsr-runtime`
- 第一跳 / 第二跳工件归属还不清楚：切 `$jsr-locate`
