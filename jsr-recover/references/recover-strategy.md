# 恢复策略

## 一、恢复不是全量反编译

恢复任务的核心交付通常包括：

- 当前目标字段经过了哪几层包装。
- 哪个桥接层把真实算子藏起来了。
- 哪些输入输出点可以作为验证锚点。

## 二、先问三个问题

1. 当前被遮住的是入口、调度、桥接、状态还是算子。
2. 当前任务只需要“解释链路”，还是已经需要“最小重建”。
3. 恢复到哪一层就足够支持后续定位或复现。

## 三、三种恢复目标

### 1. 语义解释

只需要回答：

- 哪一层负责什么
- 当前目标值经过什么路径
- 哪些输入控制输出

适合：

- 先定位，再交给其他 skill
- 不要求立即复现全链路

### 2. 关键算子抽离

只恢复当前必要的那部分：

- 关键 `opcode`
- 关键序列化壳
- 关键桥接函数

适合：

- builder 已经定位清楚
- 只差核心算子看不透

### 3. 最小重建

把当前必要链路重组成最小可验证片段。

适合：

- 已知道输入输出边界
- 已有明确验证样本

## 四、纯算迁移前先否定六类依赖

在完成关键算子抽离后，仍需先排除以下六类依赖，再判断是否允许纯算迁移：

1. 上游响应字段
2. `HttpOnly cookie`
3. 一次性 challenge / nonce / ticket
4. 浏览器内部状态
5. 指纹采集结果
6. 时间窗 / 序号 / 续期

判断原则：

- 六项里只要有一项还没闭合，就不要把当前结论写成“纯算已拿到”。
- 这时应该退回 `$jsr-locate` 或 `$jsr-runtime` 继续补链，而不是继续美化代码。

## 五、VMP 恢复级别判断

### A 级：只抽关键 `opcode`

适合：

- 已知目标字段的写回边界
- 只需要解释少量 `opcode` 就能说明目标字段如何形成

交付：

- 关键 `opcode` 卡片
- 输入输出对照
- 目标字段形成路径

### B 级：恢复 dispatcher + 关键状态载体

适合：

- `opcode` 语义依赖 dispatcher、寄存器、栈或上下文
- 不恢复状态流就无法判断关键分支

交付：

- dispatcher 循环
- 关键状态载体
- 关键 `opcode` 族与状态流

### C 级：最小反编译 / 最小解释器

适合：

- 需要跨多条路径回放
- 需要做协议重建、批量执行或最小可运行重建
- `A / B` 级都无法支撑后续工作

交付：

- 最小反编译结果或最小解释器
- 关键路径验证样本

原则：

- 默认从 `A` 开始，只有证据表明不够，才升到 `B` 或 `C`。
- 能在低一级别解决，就不要进入高一级别。

## 六、黑盒复用边界判断

对于 `webpack/runtime`、`worker`、部分 `wasm` 包装层，不一定要先反编译，很多时候先做“黑盒复用边界”更划算。

适合黑盒复用的信号：

- 已知输入输出边界
- 已找到目标模块或桥接入口
- 主要困难在容器壳、模块装载或桥接调用，而不是业务算子本身

不适合黑盒复用的信号：

- 目标模块依赖大量隐式共享状态
- 不恢复状态载体就无法稳定回放
- 目标模块内部本身就是 `jsvmp` / 深层协议壳

记录模板：

```markdown
模块 / 桥接入口：
直接依赖模块：
runtime helper：
环境桩：
输入契约：
输出契约：
版本锚点（hash / bundle / moduleId）：
是否适合黑盒复用：是 / 否
```

## 七、先拆哪一层

| 现象 | 先拆哪层 |
|---|---|
| 代码入口都找不到 | 外层容器 |
| 大量 `switch` / 调度表 / 状态机 | 调度层 |
| 看得见调用，但参数结构怪异 | 状态载体 |
| 逻辑在 `worker`/`wasm` 回来后才出现 | 桥接层 |
| 写回点已知，但中间算法看不透 | 核心算子 |

## 八、什么时候停手

出现下面任一情况就该停：

- 已足够解释目标字段形成路径。
- 已拿到桥接契约和关键算子，无需继续进行全量外观整理。
- 已在当前恢复级别拿到足够支撑后续定位 / 复现的结果。
- 继续下钻只会增加代码量，不会提升结论质量。

## 九、恢复完成标准

- 已能明确说出当前层的职责。
- 已有稳定锚点用于验证。
- 已知当前为什么停在 `A / B / C` 中的哪一级。
- 桥接 / runtime 场景下已知是否可以黑盒复用，以及黑盒边界在哪里。
- 已知道该交回 `$jsr-locate` 还是 `$jsr-runtime` 继续推进。
