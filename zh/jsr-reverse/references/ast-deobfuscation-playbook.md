# AST 去混淆剧本

## 适用场景

当主要壳层是 AST 混淆代码时使用本参考，例如字符串表、helper 包装、控制流平坦化、bundle 外壳，或被多层包装的业务算子。

本参考只负责：

- 恢复语义锚点
- 选择变换顺序
- 维护变换台账
- 在下游可继续推进时及时停止

## 先做指纹判断

在选择变换前，先判断主导壳层。

| 信号 | 常见壳层 | 首动作 |
| --- | --- | --- |
| 大字符串表 + 访问器 helper | 字符串表混淆 | 先恢复字面量 |
| 大量小 helper 包装操作符 | helper proxy / 对象字典 | 在字面量稳定后内联 |
| `while` + `switch` 调度 | 控制流平坦化 | 常量稳定后恢复执行顺序 |
| 模块启动器包裹全量逻辑 | bundle 外壳 | 先拆模块 |

没有完成壳层判断前，不做批量变换。

## 推荐变换顺序

除非证据证明依赖关系不同，否则按下面顺序：

1. 恢复可读锚点：字面量、对象 key、调用关系
2. 外壳阻断局部推理时，先拆 bundle
3. 内联简单 helper 和对象字典
4. 标准化属性访问和简单表达式
5. 恢复真实执行顺序
6. 只有活路径被证明后，才删死代码或诱饵分支

每一步开始前，都要先写清楚“这一步要保持什么不变”。

## 何时先拆 bundle

满足下面任一条件时先拆：

- 目标算子被模块启动器或懒加载包装层挡住
- 当前 bundle 无法提供稳定函数边界
- 拆模块比整包推理更便宜

如果当前壳层已经足够局部和清楚，不默认拆 bundle。

## 变换台账

每一步都记录：

- 输入产物
- 输出产物
- 执行的变换
- 保持不变项
- 验证证据

如果一条变换说不清它保持什么不变，就不应该执行。

## 完成标准

满足下面四项才算 AST 恢复完成：

- 主导壳层已识别
- 变换顺序有依据
- 已恢复足够的语义锚点支撑下一步 locate 或 replay
- 每一步变换都有验证证据

## 常见误判

- 只做 beautify 就宣布恢复完成
- 拆 bundle、内联 helper、还原控制流混在一起做，却没有台账
- 活路径还没证明就先删死代码
- 把“源码变好看了”当成证据
