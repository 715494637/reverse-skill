# 反调试与风控分支

## 一、先分清调试摩擦和真实风控

不是所有“调试一开就坏”的现象都叫反调试，也不是所有异常结果都等于风控分支。

先拆成两类：

- `调试摩擦`：让观察变难，但不一定改变业务值
- `真实风控分支`：改变链路、中间值或最终响应

## 二、常见反调试表面

| 类型 | 现象 | 处理原则 |
|---|---|---|
| 无穷 `debugger` | 每一步都被打断 | 只去掉这个摩擦点，不动业务逻辑 |
| 栈校验 | 本地回放总走 fallback | 保住栈形态或绕过校验 |
| 控制台诱饵 | 一开控制台值就变 | 不把诱饵值当真实值 |
| 性能探针 | 调试状态显著改变时序 | 固定时间和性能源 |
| 源码完整性 | 改一行就断 | 先证明它是否真的影响业务值 |

## 三、如何识别风控分支

下面这些信号说明链路不在正常态：

- 目标请求还没发出就先进入 fallback
- 同样输入下，浏览器正常，本地回放始终走另一条路
- 缺一个上游请求就立刻出现 403、空响应、challenge 或升级
- 目标值虽然算出来了，但服务端始终不接受

到这里就不要继续往算法深处钻，先证明正常执行到底依赖哪些状态。

遇到 `deviceId`、`blackbox`、`sensor_data`、challenge、滑块这类任务，要继续追：

- 哪个指纹表面最先分叉
- 哪个聚合器消费了它
- 哪个 `riskGate`、challenge 或 fallback 点真正开始分支

不要因为“某个指纹值不同”就直接下结论，必须找到消费点。

## 四、正常态 / 风控态分叉图是必需的

除了对比表，还要写分叉图，至少包含：

- 哪个请求、响应、状态缺口或调试事件开始分叉
- 正常态 builder 和 writer 走哪条路
- 风控态 fallback 或 challenge 走哪条路
- 缺的是哪种具体状态，而不是笼统写“环境不一致”

分叉图模板：

```markdown
分叉起点：请求 B 未返回 token / guest_id(HttpOnly) 缺失 / 调试触发风险探针

正常态路径：
请求 B 正常响应 -> builder_main() -> writer -> 正常响应

风控态路径：
请求 B 失败 / 调试触发 -> sign_fallback() -> challenge / 风控页

缺失状态：
- token
- guest_id(HttpOnly)
- 指纹快照
```

对比模板：

```markdown
| 项目 | 正常态 | 风控态 | 差异解释 |
|---|---|---|---|
| 上游请求 B | 返回 token 与 cookie | 返回空 / 403 | 会话未闭合 |
| builder 路径 | sign_main() | sign_fallback() | 已分叉 |
| 最终响应 | 正常数据 | 风控页 / challenge | 非同链 |
```

分叉起点和缺失状态没写清，就不能算已经分清正常态 / 风控态。

## 五、处理原则

- 只去掉妨碍观察的调试摩擦，不要大范围改代码。
- 只选会改变调查路径的最小匹配反调试规则，不要一次启用多种 patch。
- 只要发现风控分支已发生，就回头补状态与正常态样本。
- 不要默认把导航监听或 exit 监听归成反调试；如果它负责产状态，就把它记成 runtime 的状态闭合信号。
- 如果导航类或生命周期 patch 改变了页面状态，要把这件事写进记录，并在条件允许时移除 patch 后复验链路。
- 只要发现真实逻辑位于壳层内部，就应停止在 runtime 层继续消耗，并切换到 `$jsr-recover`。

## 八、完成标准

- 已分清调试摩擦与真实风控。
- 已说明哪一个点开始发生链路分叉。
- 指纹场景下已说明哪个消费点真正引发风控。
- 已证明当前使用的是最小匹配规则，而不是过宽 patch。
- 已分清状态闭合信号和反调试点，不把两者混写成同一结论。
- 已明确下一步该补状态、补对象还是切 skill。
