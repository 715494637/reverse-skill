# Locate Workflow

## 目的 / 使用边界

`locate` 是 locate 阶段的主方法文件。

它负责证明目标请求、字段、cookie 或消息的真实写入边界、sink、触发路径与上游依赖链。

只有在 evidence gate 已经产出由真实样本支撑的请求链后，才开始 locate。若目标请求仍靠猜、当前链路仍混杂多个假设、正常态与风控态尚未拆开，就应先回到 `reverse-records/请求链路.md`，先把证据工件补闭环。

## Locate 负责什么

Locate 只负责下面这些问题：

- 真实目标请求或目标消息到底是什么
- 目标值最终写入在哪里
- 哪个动作、事件或响应触发了这次写入
- 哪些上游请求、响应、cookie、状态载体或环境事实参与了这次写入
- 正常态链路与风控态链路在哪里分叉

Locate 的核心模型是：

```text
writer <- builder <- entry <- source
```

这四层要始终分开：

- `writer`：最终把值写入 request、header、query、body、cookie、frame、storage 或消息包络的地方
- `builder`：组装、变换、加密、签名、打包该值的逻辑
- `entry`：启动 builder 路径的动作、事件、回调或响应
- `source`：builder 的真实输入，包括响应、cookie、storage、内存状态、环境事实、时间、随机数或用户输入

## 默认工作模型

默认顺序：

1. 用真实样本定义目标单元
2. 先观察 sink
3. 按 `writer <- builder <- entry <- source` 反向走链路
4. 只要 source 依赖前置状态，就立即向上游展开
5. 正常态与风控态链路始终分开记录

常见 sink 的首选观察点：

| Sink | 首选观察点 |
|---|---|
| `body` 字段 | 最终序列化前或提交前写入点 |
| `header` 字段 | header 设置点或最终请求构造点 |
| JS 写入的 `cookie` | setter 或最终写点 |
| 响应 `Set-Cookie` 依赖 | 响应包与第一个消费它的依赖请求 |
| `WebSocket` frame | `send` 前的 envelope 层 |
| `worker` 回传值 | `postMessage` 契约 |
| 隐藏 DOM 字段 | 赋值点与 submit 动作 |

搜索只能作为辅助，不能单独证明来源。

如果目标值依赖响应字段、`Set-Cookie`、challenge 结果、session 初始化，或其他当前边界尚未持有的状态，就必须立刻向上游展开。

如果正常样本和风控样本分叉，要把分叉点写明：相同触发动作不代表相同链路。

对于协议与长连接任务，locate 只保留边界级需求：

- 与目标消息相关的连接状态链
- 目标流量所属的消息族
- 目标消息边界：包络字段、payload 字段，以及任何加密/压缩边界

不要把 locate 扩成整套协议工作流，除非真正的边界阻塞就在协议层。

## 必要证明

一个可用的 locate 结果，至少要证明以下内容：

- 从真实抓包样本中识别出目标请求或消息
- 最终 sink 或写入边界
- 具体的 `writer`、`builder`、`entry`
- 真实 `source` 类型，并区分为本地计算、上游响应/状态、环境事实或混合依赖
- 已向上游展开到真正支撑正常态链路的请求或状态转移；或者明确说明不存在上游请求
- 当证据中同时出现正常态与风控态时，已将二者分开

搜索命中、猜测函数名或孤立 payload 都不能单独算证明。

## 停止 / 完成标准

当请求或消息边界已经真实到让下一个阻塞不再是“继续发现请求”时，就应停止 locate。

通常意味着：

- 目标样本真实，且足够可复用
- sink 与触发路径已知
- `writer <- builder <- entry <- source` 已具体到足以继续下游工作
- 重要上游依赖已展开或被排除
- 剩余阻塞已经变成壳层可读性、运行时分叉或最终证明，而不是边界发现

交接时，要明确写清：哪些已经证实、哪些仍未闭环、下一个下游阻塞是什么。

## 不负责什么

Locate 不负责：

- 当真实请求链仍未确认时，代替 evidence gate 记录工件
- runtime patch 或浏览器/本地拟合
- 超出边界证明所需范围的全量壳层恢复、反编译或大范围去混淆
- `jsr-reverse` 中已经定义的全局路由规则与阶段矩阵
- 最终等价性证明、检查点证明或结束态验证
