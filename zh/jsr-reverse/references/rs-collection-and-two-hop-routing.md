# 瑞数采集与二跳路由

## 适用场景

当目标出现下面任一瑞数信号时，使用本参考：

- `204` 落地页或挑战页
- 页面内联 `$_ts.nsd` 与 `$_ts.cd`
- 外链 `r2mKa` 脚本
- 页面代码通过 `$_ts.l__` 生成
- `meta[r=m]` 对路由或状态有影响
- 第一跳产出的 `cookie`、跳转目标或状态需要在第二跳消费

本参考只解决：

- 证明瑞数工件链
- 证明第一跳 / 第二跳关系
- 指明下游应以哪一跳为准
- 不提前进入补环境或深层壳恢复

## 必抓工件集合

下面这些要作为一组一起采集、一起记录：

- 第一跳 URL 或落地页 URL
- 第一跳 HTML
- 携带 `nsd`、`cd` 的内联 `$_ts`
- 所有外链脚本，并分清哪个是 `r2mKa` 主脚本，哪些是 `$_ts.l__` appcode
- 所有 `meta[r=m]` 的 `content`
- 第一跳产出的 `cookie`、跳转目标或其他状态载体
- 第二跳 URL、返回状态，以及第二跳 `html/js/ts` 工件（若存在）

不要只拿到一个 JS 文件就宣称“瑞数链路已采集完成”。

## 二跳路由规则

| 条件 | 动作 |
| --- | --- |
| 第一跳产出了后续要消费的 `cookie`、跳转或路由线索 | 必须带着产出状态采第二跳请求与响应 |
| 第二跳返回了新的 `html/js/ts` | 后续 replay 或 recover 以第二跳工件为准 |
| 第二跳复用了第一跳工件 | 记录第一跳为主工件，同时记录第二跳已验证 |
| 目标后续要消费第一跳状态，但还没有第二跳证据 | 当前 locate 只能停在 `部分完成` |

## Meta-Content 规则

如果存在 `meta[r=m]`：

- 每个 `content` 都要解析并记录
- 明确它是跳转目标、路由线索，还是暂未闭合的状态线索
- 不能把它当页面噪音，遗漏在 `请求链路.md` 之外

## 停止条件

- 没有内联 `$_ts.nsd/cd`：还不能证明瑞数采集路线成立
- 目标后续要消费第一跳状态，但只有第一跳工件：`部分完成`
- 没把 `r2mKa` 主脚本和 `$_ts.l__` appcode 分开：`部分完成`
- 存在 `meta[r=m]`，但没有记录或分类：`部分完成`

## 完成标准

满足下面四项才算瑞数采集定位完成：

- 第一跳工件已完整
- 只要后续会消费第一跳状态，第二跳关系就已明确
- 已说明后续 runtime 或 recover 该以哪一跳工件为准
- 下游无需重新做瑞数基础采集
