# 协议与长连接

## 一、首包不足以支撑协议判断

长连接、协议壳、`protobuf` 场景中的高频错误，是基于单包样本直接推断协议结构。

真正要看的至少包括：

- 握手
- 首包
- 心跳
- 序号 / ack
- 续期
- 错误包 / 重试

## 落盘路径

协议与长连接场景，连接状态统一写入当前会话 `请求链路.md`。
协议壳桥接、调度关系、语义恢复结论统一写入同一份 `请求链路.md` 的紧凑小节。

建议写入当前会话 `请求链路.md` 中“协议 / 长连接状态”章节的内容：

- 握手请求与响应
- 首包类型
- 心跳周期
- 序号 / ack 规则
- 续期条件
- 状态迁移图
- 消息族分组
- 目标消息类型与载荷结构

## 二、先拆包络层，再拆载荷层

### 包络层

重点是：

- 消息类型
- 长度
- 序号
- 时间窗
- 会话标识
- 压缩 / 加密标记

### 载荷层

再看：

- 字段顺序
- 编码方式
- `protobuf` 映射
- 压缩后的正文
- 真实业务字段

### 消息族

至少区分：

- 握手 / 认证
- 心跳 / 保活
- 业务请求
- ack / 重传 / 错误
- 续期 / 刷新

没分清消息族，就不要直接把某条消息当目标主链。

## 四、状态迁移要单独记

```markdown
未连接 -> 握手中 -> 已认证 -> 心跳维持 -> 续期 -> 失效
```

如果不记状态迁移，就很容易把续期失败误判成算法错误。

## 五、连接状态链要写成可追溯链路

推荐写法：

```text
握手包 -> 握手响应(session) -> 已认证
已认证 -> 心跳包(seq) -> ack
ack 超时 -> 重传 / 降级
token 临期 -> 续期包 -> 新 session
续期失败 -> 失效 / 风控 / 强制重连
```

只要目标消息依赖前面的 `session / ack / 续期`，就不能只复现目标包本身。

## 六、常见误判

- 只看第一包，不看后续 ack / 心跳。
- 把包络层字段误当业务字段。
- 知道 `protobuf` 存在，就直接跳到 message schema，忽略状态机。
- 把续期失败、序号错位、ack 缺失误判成 payload 算法错误。

## 七、完成标准

- 已知包络层。
- 已知状态迁移。
- 已知消息族。
- 已知目标消息的真实边界与依赖。
