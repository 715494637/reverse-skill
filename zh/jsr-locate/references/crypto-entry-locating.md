# 加密入口定位

## 适用场景

当当前任务是证明一个真实请求里的 `sign`、`token`、动态请求头或加密参数从哪里生成时，使用本参考。

本参考只解决：

- 入口帧是谁
- 最终写入点是谁
- 参数关系怎么证明
- 在进入算法恢复前把定位闭环

## 首选路径

只要真实请求已经存在，优先走：

```text
请求 -> 请求详情 -> initiator / 调用栈 -> 候选帧 -> 参数证据
```

### 第一步：从请求开始

先确认：

- 哪一条请求携带目标值
- 目标值位于 URL、header、body 还是消息载荷
- 至少有一份正常态样本

### 第二步：拉 initiator / 调用栈

优先使用请求自带的 initiator 或暂停时调用栈，不先做大范围源码搜索。

目标是：

- 找到离最终写入点最近的业务帧
- 分开传输层噪声和业务组装层

### 第三步：调用栈分级

| 帧类型 | 常见信号 | 动作 |
| --- | --- | --- |
| 框架噪声 | 传输客户端、UI 框架、bundle runtime | 跳过 |
| 安全壳层 | auth、安全 SDK、指纹 SDK、风控 SDK 包装层 | 检查 |
| 业务帧 | 项目源码、请求组装器、字段构造器 | 优先 |

不要停在只会转发请求的帧上。

### 第四步：证明候选帧

候选帧只有满足下面至少一项，才算入口成立：

- 直接接收目标值
- 用稳定的本地输入组装目标值
- 以目标参数调用最终写入点

证明必须来自参数、局部变量或 writer 侧观察，不能只靠函数名相似。

## 回退路径

如果 initiator 不可用或没有意义，再走：

```text
目标字段文本 -> 窄范围赋值搜索 -> 定向断点 -> hook 确认
```

规则：

- 先搜写入模式，再搜泛化的 crypto 名称
- 只有在必须证明局部变量或分支条件时才下断点
- 只有 sink 或近 sink writer 已知时才上 hook

## 完成标准

满足下面四项才算入口定位完成：

- 已识别携带目标值的请求
- 已证明一个业务相关候选帧
- 候选帧与最终 writer 的关系已明确
- 后续可以继续做 locate，而不是继续靠猜

## 常见误判

- 先搜 `md5`、`aes`、`sign`，却还没证明 writer
- 停在框架传输层
- 没做参数证据就把安全 SDK 包装层当最终入口
- 写入链没闭环就提前转去算法恢复
